# v1.2 — field-test fixes

Three issues reported from a real 3-phone test.

## 1. Riders list looked unchanged after the update

Root cause: **no pinned debug signing key.** Every CI build was signed with
whatever debug keystore happened to exist on that particular GitHub Actions
runner — which is freshly auto-generated on every clean run, since nothing
persists it. Android refuses to install an APK over an existing app with the
same package name if the signatures don't match, and does so with no clear
error in most install flows. If the newest APK wasn't installed over a clean
uninstall, the phone was almost certainly still running an older build.

Fixed by generating a stable `keystore/debug.keystore`, checked into the repo,
and pointing `signingConfigs.debug` at it explicitly in `app/build.gradle.kts`.
Every build from here on shares one signing identity, so "download the new
APK and install over the old one" actually upgrades in place.

**This one requires action from you once:** uninstall the current MeshVoice
app before installing this build, since it may still be signed with a
different one-off key from an earlier run. Every build after this one will
update cleanly.

## 2. Echo — "I can hear on my phone what I'm saying"

`VOICE_COMMUNICATION` capture + platform `AcousticEchoCanceler` were already
wired up correctly, attached to the mic session as Android's API expects.
That setup cancels *this device's own* speaker output being picked back up
by *this device's own* mic — it cannot fix a **weak or absent AEC on the
other rider's phone**, which is the more likely explanation if what's
happening is the other person hearing themselves, not you hearing yourself.
Cheap/older Android phones vary a lot in AEC quality, and speakerphone at
outdoor/riding volume can overwhelm even a decent AEC.

Added a partial software mitigation: while a device's speaker is actively
rendering incoming audio (tracked via the mixer's last-write time), the local
mic's speech threshold is temporarily raised (`ECHO_GUARD_MULTIPLIER`), making
it less likely to re-transmit what it just picked back up off its own
speaker. A genuine loud interruption still clears the higher bar. This is a
heuristic, not real echo cancellation, and won't fully solve echo caused by
a weak AEC on someone else's phone — flagging that honestly rather than
claiming this fixes it outright.

## 3. Jittery, delayed audio with a 3rd rider

Real bug, not a network/bandwidth limitation: `AudioEngine.playIncoming()`
pushed every incoming frame — **regardless of which rider sent it** — into
one shared queue, written to a single `AudioTrack` in arrival order. With
one remote rider that's indistinguishable from correct playback. With two
or more, their packets **interleaved chunk-by-chunk instead of mixing**,
which is exactly what "jittery and delayed" sounds like once a third phone
joined and two people could be talking at once.

Neither `MeshNode.Listener.onAudioPacket` nor `InternetNode.Listener.onInternetAudio`
even passed along *who* sent a given frame, so there was no way to tell
sources apart before this fix.

Rebuilt as a real mixer:
- Both listener interfaces now pass the sender's origin id alongside the audio.
- `AudioEngine` keeps one small bounded queue (~80ms) per origin instead of
  one shared queue.
- A fixed ~20ms-cadence mixer thread pulls the next frame from every origin
  that has one ready and **sums the PCM samples** (clamped against
  wraparound) into a single mixed frame before writing to the `AudioTrack`.
  Two or more simultaneous speakers are now actually audible together
  instead of chopped into alternating fragments.
- The mixer thread parks itself after ~2s of silence and restarts the moment
  new audio arrives, so it doesn't spin forever on a quiet ride.
